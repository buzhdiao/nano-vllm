# 02 - 调度器：prefill/decode 批处理与准入控制

调度器（`nanovllm/engine/scheduler.py`，138 行）每步回答一个问题：**这一步让哪些序列、算哪些 token**。它维护两条队列：`waiting`（已提交、未分块）与 `running`（已分块、decode 中），策略是 **prefill 优先、decode 兜底、不够显存就抢占**。

## prefill 阶段：准入 + chunked prefill

`schedule()` 的前半段（scheduler.py:41-80）从 `waiting` 队首逐条尝试收进本批，受三个约束：

1. `max_num_seqs`：批内序列数上限（scheduler.py:41）；
2. `max_num_batched_tokens`：本批 token 预算，`remaining` 是剩余额度（scheduler.py:44）；
3. 显存：`block_manager.can_allocate` 预检空闲块够不够（scheduler.py:50-52）。

两个关键设计：

- **prefix cache 折算**：首次调度时 `can_allocate` 返回可复用的缓存块数，真正要算的 token 数 = `num_tokens - num_cached_blocks * block_size`（scheduler.py:56）；
- **chunked prefill**：当序列放不进剩余预算且批内已有序列时直接 break，**只有批内第一条序列允许被切分**（scheduler.py:61 的注释），切分点就是 `num_scheduled_tokens = min(num_tokens, remaining)`（scheduler.py:69）。未算完的序列留在 `waiting` 队首，下一轮从 `num_cached_tokens` 断点继续。这保证一条超长 prompt 不会独占多步预算，也不会把批搞成"多 条碎片"。

只要本步收到了任何 prefill 序列，就跳过 decode 直接返回 `(seqs, True)`（scheduler.py:79-80）——新请求的 prompt 尽快算完、尽快吐出第一个 token。

## decode 阶段：每序列一个 token

decode 循环（scheduler.py:84-108）对 `running` 里的序列各调度 1 个 token。写 KV 前要用 `can_append` 检查"这个 token 是否跨进新块、空闲块是否够"（scheduler.py:87-102）：

```python
while not self.block_manager.can_append(seq):
    if self.running:
        self.preempt(self.running.pop())   # 牺牲队尾腾显存
    else:
        self.preempt(seq); break           # 只剩自己也不够，抢占自己
```

这是 vLLM 的 **recompute 抢占**策略：不把 KV 换出到 CPU，而是直接释放全部物理块、状态打回 `WAITING`、插到 `waiting` 队首（scheduler.py:111-117），重新调度时按 prefill 重算缺失部分。用一点重复计算换取实现简单——nano-vLLM 没有 swap 通道。

最后 `self.running.extendleft(reversed(scheduled_seqs))`（scheduler.py:108）：`extendleft` 会把可迭代对象**逆序**塞回队首，所以先 `reversed` 一次才能让批内序列保持原队序，同时让未调度序列自然沉到队尾。

## postprocess：账本登记

`postprocess()`（scheduler.py:120-138）做四件事：`hash_blocks` 把新写满的块注册进 prefix cache；`num_cached_tokens += num_scheduled_tokens` 推进进度；chunked prefill 未算完则直接进入下一轮（scheduler.py:128）；否则把采样出的 token 追加进序列，命中 EOS（且未 `ignore_eos`）或达到 `max_tokens` 就置 `FINISHED` 并立刻 `deallocate` 释放全部物理块（scheduler.py:131-137）——完成即回收，是高吞吐下显存不碎的关键。

## 与 vLLM 调度器的差异

vLLM 有 priority、抢占比额控制、speculative decoding 等复杂机制；nano-vLLM 只有 FIFO + prefill 优先 + recompute 抢占三件套，约百行代码覆盖了离线推理的全部调度需求。
